# Полезная модель Home Assistant вместо зеркала RCI

Интеграция представляет полезные для наблюдения, автоматизаций и управления понятия умного дома, а не каждую техническую запись RCI. Это решение принято после первичной проверки новой интеграции на личной установке: совместимость старого публичного контракта не ограничивает переработку, но все неизвестные форматы и изменяющие команды требуют доказательств.

## Критерий полезности

Сущность или устройство остаётся в интеграции, когда пользователь может осмысленно наблюдать его, использовать в автоматизации или управлять им. Техническая запись RCI служит источником данных и не становится сущностью автоматически.

Платформы Home Assistant получают единый нормализованный снимок интерфейсов. Классификация, выбор WAN, фильтрация внутренних интерфейсов и правила доступности принадлежат общей модели; отдельная платформа не выводит собственную семантику из сырого ответа.

## Топология устройств

| Понятие | Модель Home Assistant | Решение |
| --- | --- | --- |
| Роутер | Корневое физическое устройство | Содержит общие состояния, диагностику и действия роутера. |
| `WifiMaster*`, родительский `GigabitEthernet*`, bridge и внутренние Ping Check ID | Только источник данных | Отдельные устройства и трафик-сенсоры не создаются. Физические дочерние порты `GigabitEthernet*/<номер>` получают диагностические сенсоры состояния на корневом роутере. Однозначная температура `WifiMaster` может стать температурой роутера. |
| Клиент сети | Дочернее устройство через роутер | Создаётся только для MAC из объединения списков трекинга и IP-политики. Карточка содержит client controls, диагностику и локальные First/Last Seen; массовое создание всех клиентов исключено. |
| VPN-интерфейс | Логическое дочернее устройство роутера | Создаётся только для точных типов OpenVPN, PPTP, SSTP, WireGuard и ZeroTier. Неоднозначный тип `Secure` остаётся неклассифицированным; switch появляется только при известном административном `state`. |
| WireGuard peer | Сущности соответствующего VPN-устройства | Отдельное устройство peer не создаётся; его identity основана на стабильном ключе, а отображаемое имя может меняться. |
| USB-модем | Физическое устройство через роутер | Типы `UsbLte` и `CdcEthernet` распознаются по полному `show/interface` даже при `connected=false`, `plugged=no` или `state=down`; содержат связь, доступную диагностику, switch подключения и кнопку перезапуска. SMS-сущность появляется только после подтверждения поддержки. |
| Mesh-узел | Физическое устройство через роутер | Содержит системные показатели, backhaul и подтверждённые порты; непредоставленные поля не выдумываются. |
| USB-накопитель | Состояние корневого роутера | Отдельное устройство не создаётся. Состояние означает наличие смонтированного раздела, а не просто USB-устройства. |

## Состав сущностей

- Роутер сохраняет доступность, Internet Checker, число активных Wi-Fi-клиентов, прошивку, CPU, память, uptime, доступную температуру, default route/IP, скорость WAN, состояние физических гигабитных портов, смонтированный USB-накопитель, DNS Proxy, IPsec VICI и кнопку перезагрузки.
- Общие RX/TX-счётчики WAN не создаются. Скорость рассчитывается только для единственного подтверждённого IPv4 default route; смена маршрута, сброс счётчика и ECMP сначала дают неизвестное значение, а не ложный всплеск.
- Диагностические сущности остаются включёнными по умолчанию и помечаются категорией `diagnostic`. Пользователь может отключить их в реестре HA; CPU, память, температура, LTE и аналогичные показатели предназначены в том числе для alert-автоматизаций.
- VPN получает состояние соединения, uptime, трафик, скорость и отдельный переключатель административного состояния. `connected/link` и административное `state` — разные понятия.
- WireGuard peer получает online, RX/TX, возраст handshake и remote endpoint, если эти поля подтверждены ответом. Display name берётся из `description`/`name`, а без него — из полного стабильного peer ID.
- Клиент получает IP, тип подключения, DHCP/link status, link speed, port, RSSI, принятые/отправленные с точки зрения клиента байты, производную скорость передачи, время подключения текущей live-сессии, Wi-Fi band/mode и локальные First/Last Seen. Управление включает Connection Policy, Wake on LAN, одинаковый down/up Bandwidth Limit в kbit/s и его Clear-кнопку.
- Модем получает только присутствующие поля: оператор, технология, связь, APN, диапазон, roaming, температуру, LTE-сигнал, квоту и SMS. Личные SIM-идентификаторы не публикуются как атрибуты.
- Mesh получает CPU, память, uptime, associations, backhaul, доступную версию прошивки и состояние подтверждённых портов.
- События смены WAN и нового полного SMS, действия SMS/USSD и произвольного RCI-запроса сохраняются. Первый снимок SMS задаёт baseline и не публикует старые сообщения.

## Доступность и неоднозначные данные

Неизвестное, отсутствующее, противоречивое или неподтверждённое значение представляется как `unknown`/`unavailable`. Ноль и отрицательное состояние используются только когда их подтверждает контракт ответа.

- Internet Checker считается достоверным при `reliable: true`; `enabled: false` не отменяет достоверный снимок. Поддерживаются JSON boolean и документированные `yes/no`. Наблюдаемый `captive-accessible` служит вариантом поля проверки контрольных узлов `host-accessible`.
- Число Wi-Fi-клиентов включает уникальные активные записи, классифицированные как беспроводные по интерфейсу или RSSI. Отключённые и неклассифицируемые строки не превращают полный достоверный inventory в недоступный результат.
- USB-состояние подтверждается обоими ресурсами: в `show/usb` нужен известный inventory с устройством `storage`/`media`, в `show/media` — раздел `MOUNTED`. Неизвестный inventory оставляет состояние недоступным; известный пустой inventory означает отсутствие накопителя.
- Память разбирается из `used/total`; некорректное, отрицательное или превышающее total значение остаётся неизвестным.
- Необязательный RCI-ресурс может отсутствовать из-за модели, KeeneticOS или компонента; это не ошибка всего координатора.

## Единицы и представление

Native state остаётся числовым и пригодным для статистики и автоматизаций. Рекомендуемая единица и точность управляют отображением новой сущности в Home Assistant.

| Показатель | Native state | Отображение |
| --- | --- | --- |
| CPU load | Проценты 0–100 | `%` |
| Занятая память роутера и Mesh | Проценты из `used/total` | Одна цифра после запятой |
| Uptime роутера, VPN, модема и Mesh | Секунды | Рекомендуемая единица `d`; HA показывает числовую длительность в днях, а автоматизации сохраняют точные секунды |
| Накопленный трафик интерфейсов, WireGuard peers и клиентов | Байты | Рекомендуемая единица `MB`, без потери byte-based statistics |
| Скорость | Мегабиты в секунду | `Mbit/s` |
| Возраст WireGuard handshake | Значение `last-handshake`, интерпретируемое как секунды; единица официально и live не подтверждена | Без дробной части; sentinel `2147483647` означает отсутствие значения |
| RSRP и RSSI | `dBm` | Контекстная иконка уровня сигнала по официальным диапазонам Keenetic |
| RSRQ и SINR/CINR | `dB` | Контекстная иконка качества сигнала по официальным диапазонам Keenetic |

Сущности получают контекстные Material Design Icons там, где есть устойчивый смысл. Для CPU, памяти, uptime, направлений трафика, устройств и действий используются стабильные тематические иконки; динамический уровень применяется только там, где есть подтверждённые числовые границы.

## Настройки и действия

Options flow содержит только работающие возможности: интервал опроса, отдельные списки клиентов для трекинга и IP-политики, включённые Wi-Fi SSID, разрешение произвольного mutating RCI и SMS-получателя по умолчанию. Широкие флаги «все клиенты/политики», настройки backup, port-forward и другие несвязанные переключатели удаляются миграцией.

- Wi-Fi управляется явным списком SSID в настройках интеграции; отдельные switch entities для точек доступа не создаются.
- VPN-switch отражает административный `show/interface.state`, вызывает ровно один `interface/up` или `interface/down`, обновляет координатор и требует подтверждения нового состояния. Состояние соединения остаётся отдельным binary sensor.
- Switch модема отражает то же административное `state` и разрешает использование модема по политике Keenetic; состояние связи остаётся отдельным. При Standby включение не означает немедленную сотовую связь. После команды требуется подтверждение обновлённым `show/interface`.
- Непрочитанные SMS считаются по достоверному `sms/list` как число записей с `read=false`. Неоднозначный ответ и ошибка чтения дают `unavailable`; после первого успешного чтения сущность и именная служба `notify` сохраняются при временном сбое до восстановления.
- Действия `send_sms`, `list_sms`, `mark_sms_read`, `delete_sms` и `send_ussd` принимают ровно одно устройство модема в `target.device_id`; роутер и интерфейс определяются автоматически. `send_sms` отправляет одному получателю, пустое поле использует номер из настроек роутера; несколько адресатов требуют нескольких действий. Чтение не отмечает SMS прочитанными. Отметка и удаление принимают один ID из списка выбранного модема и проверяют результат свежим чтением. USSD возвращает один ответ за общий таймаут 60 секунд; параллельный запрос на том же роутере отклоняется, чтобы ответы общей HTTP-сессии не смешивались. Автоматического повтора изменяющих запросов нет. Точные тела SMS POST выведены из CLI/RCI mapping и не подтверждены live-проверкой.
- Кнопка модема вызывает ровно один `interface/usb/power-cycle` с именем интерфейса и паузой 3000 мс, в том числе для отключённого модема. Она не делает немедленный refresh и не повторяет POST.
- Клиентский Bandwidth Limit вызывает один `POST ip/traffic-shape/host` с MAC и rate 64–1000000 kbit/s; Clear использует один `DELETE` того же ресурса. Оба изменения подтверждаются следующим чтением. Wake on LAN вызывает `POST ip/hotspot/wake` с MAC.
- Кнопка роутера вызывает `system/reboot`. Произвольный POST через public action доступен только после явного включения соответствующей опции.
- Любая изменяющая команда сообщает неподтверждённый результат как ошибку. Уже отправленный POST автоматически не повторяется.

## Динамика, миграция и очистка

Новые модемы, Mesh-узлы, VPN и WireGuard peers добавляются после обновлений координатора. Удаление сущности или устройства выполняется только после полного авторитетного inventory с устойчивыми идентификаторами.

Сенсоры физических гигабитных портов не удаляются при исчезновении записи или неполном ответе `show/interface`: существующая сущность остаётся зарегистрированной и становится недоступной до следующего подтверждённого `link`.

Некорректный, отсутствующий или неоднозначный inventory сохраняет зарегистрированные объекты. Полный пустой inventory подтверждает отсутствие и разрешает очистку. Клиентское устройство сохраняется, пока MAC выбран хотя бы для трекинга или политики, и удаляется после исключения из обоих списков. Первый и последний валидные снимки клиента хранятся в локальном storage записи интеграции.

Миграция удаляет устаревшие сущности внутренних интерфейсов, Ping Check и старые клиентские сенсоры, но сохраняет полезные клиентские устройства и публичные сущности нового контракта. Очистка знает suffix новых VPN-switch и modem-button, чтобы исчезнувший подтверждённым inventory интерфейс не оставлял сирот.

## Отложенный scope

Следующие возможности остаются вне продукта до появления подтверждённой безопасной схемы и полезного HA-контракта:

- backup и обновление прошивки;
- переключатели port forwarding;
- Wi-Fi QR-код;
- управление питанием USB-порта целиком — это не перезапуск конкретного модема;
- сброс только клиентской IP-политики к default без удаления host-записи;
- активные соединения, Mesh Wi-Fi температура/трафик и USB Mesh-узлов;
- выбор текущей LTE-ячейки или агрегации;
- сущности для неизвестных типов интерфейсов и неподтверждённых полей.

## Граница доказательств

Официальная документация и исходный код целевой версии Home Assistant определяют платформенный контракт; модельные руководства Keenetic и реальные RCI-ответы определяют доступные поля. Наблюдение на одной или двух моделях не становится универсальной схемой KeeneticOS 4/5.

Read-only проверка текущего роутера подтвердила JSON boolean Internet Checker, `captive-accessible`, активные Wi-Fi-записи, индексированные объектом `show/usb` и `show/media`, `subsystem: media`, раздел `MOUNTED` и отдельное административное `interface.state`. Изменяющие VPN, modem и Wi-Fi POST в этой проверке не выполнялись.

Локальные тесты и компиляция подтверждают парсинг и контракт кода, но не запуск в реальном Home Assistant. В отчётах эти уровни проверки указываются раздельно.

## Изменение решения

Изменение состава сущностей, топологии устройств, единиц, настроек, динамической очистки или live-границы считается изменением этого решения. Оно завершено, когда обновлены соответствующая строка здесь, пользовательское поведение в `README.md`, доказательства или ограничение в `docs/official-sources.md` и тесты затронутого контракта.
