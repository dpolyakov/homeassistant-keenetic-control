# Официальные источники и ограничения

Срез документации проверен 29.10.2026. Требование brief — Home Assistant Core 2026.9 и новее. Основные ссылки ниже ведут на первичные источники Home Assistant и Keenetic. Для отложенного USSD отдельно указана практическая инструкция модератора Keenetic Community, поскольку формальное руководство не описывает HTTP-последовательность опроса; доступность команд Keenetic зависит от модели, KeeneticOS и установленных компонентов.

## Home Assistant

| Тема | Официальный источник | Что важно для реализации |
| --- | --- | --- |
| Config flow, уникальный ID | [Config entries: config flow](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/) | ID должен быть постоянным и не зависеть от редактируемого имени, IP или URL. Для исключения дубликата вызываются `async_set_unique_id()` и `_abort_if_unique_id_configured()`. |
| Миграция config entry | [Config entries](https://developers.home-assistant.io/docs/config_entries_index/), [Config flow version](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/#config-entry-migration) | При повышении `ConfigFlow.VERSION` интеграция реализует `async_migrate_entry` в `__init__.py`. Миграция версии 2 переводит широкие клиентские настройки в явные списки и очищает снятые сущности реестра до загрузки платформ. |
| Duration и пользовательские значения selector | [Sensor entity](https://developers.home-assistant.io/docs/core/entities/sensor/), [Sensor source 2026.9.1](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/sensor/__init__.py), [selector source 2026.9.1](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/helpers/selector.py) | `DURATION` остаётся числовым сенсором. Uptime хранится в секундах, а рекомендуемая единица `d` позволяет интерфейсу HA показывать длительность без потери числового состояния. `SelectSelectorConfig.custom_value` допускает ручной ввод MAC наряду со списком обнаруженных клиентов; интеграция отдельно валидирует и нормализует введённые значения. |
| Иконки и рекомендуемое отображение | [Frontend icons source 2026.8.26.6](https://github.com/home-assistant/frontend/blob/20260826.6/src/data/icons.ts), [Sensor entity](https://developers.home-assistant.io/docs/core/entities/sensor/) | Для числового диапазона frontend выбирает иконку с наибольшим порогом, который не превосходит текущее значение. `suggested_unit_of_measurement` и `suggested_display_precision` влияют на представление новой сущности, не меняя исходную единицу и значение интеграции. Поэтому байтовые счётчики сохраняют native unit `B`, но рекомендуются к отображению в `MB`, а возраст handshake — без дробной части. |
| Ошибки настройки и повторное подключение | [Setup failures](https://developers.home-assistant.io/docs/integration_setup_failures/) | Временный отказ соединения — `ConfigEntryNotReady`; отказ авторизации — `ConfigEntryAuthFailed`; невосстановимая ошибка — `ConfigEntryError`. Ошибки загрузки entry поднимаются из `async_setup_entry`. |
| Options flow и перезагрузка | [Options flow](https://contributors.home-assistant.io/core/integrations/options-flow/) | Опции хранятся в `entry.options`. Для опций, требующих перезапуска интеграции, документация предлагает `OptionsFlowWithReload`. Интервал опроса не следует выставлять пользовательской опцией: его выбирает интеграция. |
| Опрос и coordinator | [Fetching data](https://developers.home-assistant.io/docs/integration_fetching_data/), [appropriate polling](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/appropriate-polling/) | Для периодического опроса используется `DataUpdateCoordinator`; первый запрос выполняется при настройке entry. При `UpdateFailed` данные считаются недоступными, затем coordinator повторяет запрос. Руководство HA предпочитает подходящий фиксированный интервал и push, если устройство его поддерживает. Brief задаёт настраиваемый интервал 30 секунд с минимумом 1 секунда: это явное требование продукта, расходящееся с рекомендацией HA; 1 секунда не является платформенным пределом, но может превышать допустимую частоту запросов устройства. |
| Динамические устройства и очистка | [Dynamic devices](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/dynamic-devices/), [stale devices](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/stale-devices/) | Меняющийся набор устройств синхронизируется по фактическим данным. Удалять устаревшие устройства можно только по полному авторитетному списку: ошибка или неполный ответ не доказывают, что устройство исчезло. |
| Физические устройства и дочерние устройства | [Device registry](https://developers.home-assistant.io/docs/device_registry_index/), [изменения WebSocket API в HA 2026.9](https://developers.home-assistant.io/blog/2026/08/19/device-registry-websocket-api-changes/), [changelog 2026.9](https://www.home-assistant.io/changelogs/core-2026.9/) | В HA 2026.9 появился контракт дочернего устройства (`ChildDeviceInfo` / `parent_device_id`) для логической части физического родителя. Оно не представляет отдельное физическое оборудование и не задаёт собственные manufacturer/model/serial/firmware/connections/via-device. Для отдельного устройства за шлюзом применяется `via_device_id`. Родитель должен существовать; дети принадлежат той же config entry/subentry, а вложенная иерархия детей не поддерживается. Поэтому логический VPN-интерфейс уместен как дочерний; отдельный модем или Mesh-узел следует представлять физическим устройством с `via_device_id`, а не логическим ребёнком. |
| Device/entity IDs и tracker | [Entity unique ID](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/entity-unique-id/), [device tracker](https://developers.home-assistant.io/docs/core/entities/device-tracker/) | Entity ID должен строиться из устойчивого идентификатора. Для `device_tracker` используется платформа с доменом `device_tracker`; сканер задаёт `source_type` и состояние соединения. IP-адрес и отображаемое имя могут меняться и не подходят как уникальный ID. |
| Update | [Update entity](https://developers.home-assistant.io/docs/core/entities/update/), [изменение прогресса update entity](https://developers.home-assistant.io/blog/2024/10/31/update-entity-changes/) | Доступны версии установленного и последнего релиза и feature `install`. `backup` — булева возможность создания резервной копии перед обновлением, а не выбор типов backup. В актуальном контракте `in_progress` — bool/None, процент передаётся отдельно через `update_percentage`. |
| Image, number, button | [Image](https://developers.home-assistant.io/docs/core/entities/image/), [number](https://developers.home-assistant.io/docs/core/entities/number/), [button](https://developers.home-assistant.io/docs/core/entities/button/) | `ImageEntity` подходит для QR-кода; изображение обновляется по `image_last_updated`, а чтение `async_image` должно быть дешёвым или кэшированным. `ButtonEntity` выполняет команду без параметров через `async_press` и не возвращает произвольный результат. Для вызова с числовым аргументом подходит `NumberEntity`; команды, возвращающие данные, лучше публиковать как actions. |
| Actions и `response_variable` | [Actions for integrations](https://contributors.home-assistant.io/core/integrations/actions/), [данные ответа в автоматизациях](https://www.home-assistant.io/docs/automation/action/#action-response-data) | Actions регистрируются на уровне интеграции в `async_setup`. Для ответа задаётся `SupportsResponse.ONLY` или `OPTIONAL`; результат должен быть JSON-сериализуемым mapping. Автоматизация может присвоить ответ через `response_variable`, только если action поддерживает ответ. Ошибки команды следует сообщать исключением. Это даёт подходящий контракт для USSD и произвольного RCI-запроса, чего `ButtonEntity` не обеспечивает. |
| Events | [Event entity](https://developers.home-assistant.io/docs/core/entities/event/), [integration events](https://developers.home-assistant.io/docs/integration_events/) | Event entity объявляет допустимые `event_types` и обновляет состояние при новом событии; в entity хранится последнее событие, а не архив сообщений. События шины интеграции можно отправлять с идентификатором устройства. Для SMS следует учитывать, что атрибуты события могут содержать и сохранять текст сообщения. |
| Switch для модема | [Switch entity](https://contributors.home-assistant.io/core/entities/switch/), [исходный код SwitchEntity](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/switch/__init__.py) | `is_on` отражает административное `state`, `async_turn_on`/`async_turn_off` отправляют по одной команде и проверяют результат новым снимком. Switch и кнопка перезапуска используют один идентификатор дочернего устройства. |
| Recorder и долгосрочная статистика | [Sensor entity](https://developers.home-assistant.io/docs/core/entities/sensor/) | Статистика доступна только числовым сенсорам с совместимыми `state_class`, единицей и, где нужно, `device_class`. `MEASUREMENT` — текущие величины; `TOTAL_INCREASING` — счётчики, растущие с возможным сбросом; `TOTAL` — сумма, которая может увеличиваться и уменьшаться, с корректным `last_reset`. Краткосрочная статистика агрегируется с шагом 5 минут, долгосрочная — почасово. У `TOTAL_INCREASING` падение менее 10% считается шумом, а не сбросом. |
| Переводы | [Internationalization](https://developers.home-assistant.io/docs/internationalization/core/) | Пользовательские строки интеграции поставляются в `translations/en.json` и локализованных файлах, например `ru.json`; `strings.json` для custom integration не компилируется. Ссылки на ключи-переводы внутри custom translations не поддерживаются — строки указываются полностью. |

## Keenetic: RCI, команды и ограничения

| Тема | Официальный источник | Что подтверждено документацией |
| --- | --- | --- |
| RCI через HTTP Proxy | [Using API methods through HTTP Proxy](https://support.keenetic.com/challenger/kn-3910/en/55035-using-api-methods-through-the-http-proxy-service.html) | Для доступа через HTTP Proxy пользователю роутера требуется разрешение на этот сервис. Документация описывает проксирование HTTP-запросов к `/rci` через порт 79, JSON, GET/POST и пример `curl` с HTTP Digest. Она не описывает handshake авторизации прямого локального `/auth`; механизм локальной авторизации нельзя выводить из статьи про proxy без проверки на устройстве. |
| Синтаксис и семантика RCI | [Официальное руководство CLI для KN-1011, KeeneticOS 4.0](https://docs.help.keenetic.com/cli/4.0/en/cli_manual_kn-1011.pdf), [Download Center и руководства по моделям](https://support.keenetic.com/challenger/kn-3910/en/28382-download-center.html) | В руководстве команды CLI отображаются как дерево ресурсов под `/rci`: путь `a b c` соответствует `/rci/a/b/c`. Документ KN-1011 — модельный пример, не универсальный список для всех роутеров; для каждой модели следует брать её руководство. Для настроек описаны GET (чтение), POST (создание/изменение) и DELETE (сброс); actions вызываются через POST, а все show-команды — batch POST к корневому `/rci/show` с вложенным JSON-деревом, где GET-mapping также указан только для этого корневого ресурса. RCI ответ сохраняет структуру команды; массив команд даёт массив ответов. Фоновые процессы запускаются POST, опрашиваются GET и завершаются DELETE. `system configuration save` явно сохраняет конфигурацию. |
| Различия между KeeneticOS 4 и 5 | [Руководство CLI для KN-1012, KeeneticOS 4.3](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.3/en/cli_manual_kn-1012.pdf), [руководство CLI для KN-3812, KeeneticOS 5.0](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-3812.pdf) | Это модельные руководства, а не общая матрица совместимости. В них подтверждены фиксированные команды coordinator, interface actions, SMS и USSD; наличие на других моделях зависит от оборудования и компонентов. На текущем роутере выполнены только безопасные GET-проверки перечисленных ниже форм; изменяющие команды не запускались. |
| Имена интерфейсов модема и AT | [Руководство CLI OS 4.3 для KN-1012](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.3/en/cli_manual_kn-1012.pdf), [руководство CLI OS 5.0 для KN-2311](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-2311.pdf), [USB modem interfaces](https://support.keenetic.com/hero/kn-1012/en/50383-enabling-usb-modem-debug-mode.html), [AT-команды для модемов](https://support.keenetic.com/hero/kn-1011/en/33263-entering-at-commands-for-4g-modems.html), [описание компонентов](https://support.keenetic.com/hero/kn-1011/en/16327-keeneticos-component-description.html) | В зависимости от режима встречаются `UsbModem0` (RAS), `CdcEthernet0`, `UsbLte0` (NDIS) и `UsbQmi0` (QMI); имя и регистр зависят от устройства, актуальное имя предлагается смотреть через `show interface`. `show interface cells` для USB-интерфейса сообщает список базовых станций с `phy-id` (Cell ID) и `rssi`; перечень не помечает обслуживающую соту. `show interface operators` возвращает список доступных операторов только после запуска `interface mobile scan`; интеграция не запускает сканирование автоматически. Отправка AT-команд документирована с KeeneticOS 3.9 для NDIS/QMI: `interface {name} tty send {command} [expect] [timeout]`. Поддержка модема и нужный драйвер/компонент зависят от модели и установленной конфигурации. |
| USSD | [USSD](https://support.keenetic.com/hero-5g/kn-4110/en/30172-ussd.html) | Документация указывает KeeneticOS 3.5+, совместимый QMI или встроенный модем и команду `ussd {interface} send {request}`. Работают режимы Auto и 3G; 4G-only не поддерживается. В Auto соединение может временно перейти с 4G на 3G. USSD-коды и продолжение диалога зависят от оператора; следующий шаг диалога отправляется отдельным запросом. |
| Отложенный ответ USSD через RCI | [Инструкция модератора Keenetic Community](https://forum.keenetic.com/topic/19783-get-mobile-data-usage-through-restapi/) | Если POST `/rci/ussd/send` возвращает `continued: true`, инструкция предлагает повторять GET к тому же ресурсу с сохранением HTTP-сессии; примерный интервал — 1 секунда. Это практический пример, не формальная схема RCI, и его не проверяли на устройстве этой интеграции. Код отправляет POST один раз и использует общий таймаут для POST и последующих GET. Поскольку ответ связан с HTTP-сессией роутера, параллельные USSD-вызовы на одном роутере отклоняются; разные роутеры имеют независимые блокировки. |
| SMS | [Руководство CLI для KN-1810 / KeeneticOS 4.3](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.3/ru/cli_manual_kn-1810_ru.pdf), [SMS](https://support.keenetic.com/runner-4g/kn-2212/en/30143-sms.html) | CLI документирует `sms <name>` с вложенными `list`, `read <id>`, `delete <id>`, `send <to> <message>`; результат `list` содержит `messages` с ID и полем `read`. Read-only запрос к текущему роутеру подтвердил `GET /rci/sms/list?interface=UsbLte0`: `messages` — словарь по ID, `read` — JSON boolean. Для `CdcEthernet0` тот же GET вернул `SMS is not supported`. Прежний POST `sms/list` с `name` отвергнут как `no input`. Поэтому код передаёт `interface`; точные JSON-тела изменяющих `sms/read`, `sms/delete` и `sms/send` выведены из CLI/RCI mapping и не подтверждены live POST. Для удаления применяется один POST `sms/delete` с `interface` и непрозрачным `id` из списка: команда и аргумент `id` документированы также в [руководстве KN-3812 / OS 5.0](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-3812.pdf), §3.172.1 (pp.698–699), а Appendix B задаёт POST для actions и JSON-параметры. Имя `interface` подтверждено чтением и [примером модератора](https://forum.keenetic.com/topic/20007-hero-4g-kn-2311-sms-gateway-sms-api-and-at-commands/); отдельного первичного HTTP-примера удаления нет. Успех отметки и удаления проверяется свежим `sms/list`; неизвестный результат остаётся ошибкой, POST не повторяется. Документация указывает совместимый QMI или встроенный модем; доступность SMS проверяется для каждого устройства. |
| Ping Check и Internet Checker | [Руководство CLI для KN-1011 / KeeneticOS 4.0](https://docs.help.keenetic.com/cli/4.0/en/cli_manual_kn-1011.pdf) | `show ping-check` показывает технические записи профилей с `profile`, `interface` и `status`. Они не образуют полезный стабильный пользовательский контракт, поэтому интеграция не опрашивает этот ресурс и не создаёт отдельные сущности по внутренним ID. Сводные проверки интернета берутся из `show/internet/status`, только когда ответ помечен `reliable`. На текущем роутере поля `reliable`, `internet`, `gateway-accessible`, `dns-accessible` и `captive-accessible` возвращаются JSON boolean; `captive-accessible` используется как наблюдаемый вариант проверки контрольных узлов. `enabled: false` не отменяет достоверный результат при `reliable: true`. |
| USB-накопители | [Руководство CLI OS 4.1 для KN-2410](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.1/en/cli_manual_kn-2410.pdf), [руководство CLI OS 5.0 для KN-2311](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-2311.pdf) | `show usb` возвращает устройства; `subsystem` сообщает их класс, но не доказывает монтирование. `show media` сообщает состояние носителя и разделов, включая `state`, `total` и `free`; диагностические суммы байтов доступны только для смонтированных разделов. Поэтому binary sensor означает наличие смонтированного раздела по `show/media`, а не просто подключённое USB-устройство. На текущем роутере `show/usb.device` и верхний уровень `show/media` возвращены объектами, индексированными стабильными именами; накопитель имеет `subsystem: media`, а раздел — `MOUNTED`. Парсер также сохраняет поддержку документированных списков. |
| Mesh | [Руководство CLI OS 4.3 для KN-1012](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.3/en/cli_manual_kn-1012.pdf), pp. 621–622, 624–625; [руководство CLI OS 5.0 для KN-3812](https://storage.googleapis.com/docs.help.keenetic.com/cli/5.0/en/cli_manual_kn-3812.pdf), pp. 638–639, 642–643 | `show mws member <member>` сообщает per-member `associations`; пример OS4.3 содержит `backhaul.uplink/speed`, а пример OS5.0 — также `backhaul.ap`, `backhaul.txrate` и `backhaul.rssi`. Код опрашивает `show/mws/member` и `show/mws/associations` как optional и создаёт сенсоры из распознанных полей участника; состояние Mesh-портов создаётся только при наличии `port[].link` со значением `up`/`down`. ### Практические границы

- Для KeeneticOS 4 и 5 изучены модельные руководства 4.0, 4.1 и 5.0; публичные материалы не дают универсальную матрицу всех возможностей RCI для всех моделей и установленных компонентов. Проверять команды нужно по руководству CLI конкретной модели и по ответам самого устройства.
- Имена, режимы и данные модемов различаются по протоколу и драйверу; поля метрик могут отсутствовать. Отсутствующее поле не следует интерпретировать как нулевое значение или как удалённый модем.
- Пользователь предоставил ответы RCI с KN-1810/OS 4.3.5 и KN-3812/OS 5.1.7. В обоих `show/interface` возвращён объектом записей, а не списком; парсер поддерживает обе формы. Ответ OS4 содержит карту `ip.policy`, а форма интерфейса USB-модема имеет дополнительные поля; ответ OS5 содержит `hotspot.host[].policy`, карту `ip.policy` и WireGuard peer-записи, вложенные в interface. Дополнительная read-only проверка текущего роутера подтвердила наблюдаемые формы `show/internet/status`, `show/ip/hotspot`, `show/usb`, `show/media`, `show/interface` и `show/running-config`. Эти наблюдения не подтверждают поддержку всех моделей или версий. Ответы `show/mws/member`, `show/mws/associations` и `show/wireguard-server` по-прежнему не предоставлены. Значения температуры, частот и ширины мобильного канала оставляются сырыми там, где они отображаются; официальные материалы не задают для них единицы.
- Перечисленные документы описывают отдельные возможности Keenetic, а не единый API обнаружения возможностей. Необходимость отдельных команд, в том числе для SMS/USSD/интерфейсов, определяется моделью, прошивкой, компонентами и реальными ответами RCI.
